| 2026-11-01 | sacdfs tag layer: edits in a separate tags directory, one file per disc keyed by TOC identity; edits made out-of-band (importer from extracts, beets-pysacd export, CLI/TOML), with no writable mount; art embedded only when a disc's tags name it | Owner chose the recommended option on all three questions. The images' dataset stays read-only, and edits survive renaming or moving an ISO. A writable mount would mean accepting multi-GB whole-file rewrites from taggers over FUSE/NFS/SMB, then verifying the audio unchanged: high risk for a convenience the importer and beets already provide. Embedding art only on request keeps the default output byte-identical, which is how Roon carries play history over. Trade-off: no tagging straight from a player's file-tag editor. | [sacdfs#81](https://github.com/aclater/sacdfs/issues/81) |
| 2026-11-01 | sacdfs is architected for storage reclamation: users can delete their DSF/DFF extracts and keep only the SACD images, losing nothing | Owner: "a value of using sacdfs is reclaiming storage space - so that's what i want to architect for" ... "that's a major value of sacdfs, from my perspective". On the owner's library, about 405 GB of DSD extracts sit beside 759 GB of images. Deletion needs, in order of what blocks it: folder art and sidecar files served, per-file verification before deleting, byte-identical default output (so players carry history over; Roon did), performance at least that of local files, beets following the ISOs, a tag layer for edits, small caches only, and simple same-host deployment. Alternative: keep extracting with pysacd. That is simpler, but stores every disc twice or more. Trade-off: sacdfs takes on features local files get for free (art, tags). CD-layer rips and other converters' PCM stay outside its scope. | [sacdfs#82](https://github.com/aclater/sacdfs/issues/82) |
| 2026-11-01 | DSD-to-PCM conversion: keep scarletbook-rs's clean implementation (scarletbook-pcm, #130) rather than adopting an existing code base; measure it against the consumers' converters after 0.5.2 (quality, ≥ 100× real time, within the 15 % leeway, determinism) | Owner asked whether PCM must be clean room or could adopt open-licensed code, and approved the plan ("good plan"). Not legally required: conversion is general DSP, not SACD format knowledge. But scarletbook is MIT/Apache, so GPL/LGPL code (FFmpeg, SoX, libsoxr) is out. The one permissive candidate, dsd2pcm (BSD, 2009), postdates the pre-2006 patent-hygiene rule (#40). The clean converter already exists, was written from pre-2006 literature, and has no licence or patent questions. If it falls short, file the gap upstream with numbers; as a fallback, allow the clean side to consult permissively licensed standalone DSP code outside any SACD/DST repository, recording each source. Trade-off: possibly some speed or quality work upstream, in exchange for clean provenance. | [scarletbook-rs#130](https://github.com/aclater/scarletbook-rs/issues/130), [#40](https://github.com/aclater/scarletbook-rs/issues/40) |
| 2026-11-01 | scarletbook-rs work order: integration before performance. 1 #125 CET marking, 2 #123 cheaper cold seeks, 3 #146 DST back to the speed of the code it replaced, 4 #131 DSF/DSDIFF output, 5 #130 DSD-to-PCM conversion, 6 #132 TOC reading; #27, #31, #61 and #62 stay paused (Priority field on the board) | Owner asked "should we prioritize performance or integration pr's on scarletbook-rs?" and approved the recommendation ("yes, please do"). pysacd and sacdfs already beat `sacd_extract` by 2.5–4×. What costs users and maintainers now is duplicated code (each consumer keeps its own DSF writer and PCM converter) and seek latency, not throughput. #125 hardens wheels already shipped. #123 unblocks sacdfs#28 and may fix sacdfs#71. #146 is inside the 15 % leeway, but the offload rule says slower offloads are optimised back, so it comes before new offloads. #132 is 0.69 ms against 0.15 ms per disc, which no user notices. The rest stays under the throughput pause. Alternative: performance first, which would polish numbers already well past the goal while the duplicated code stays. | [board](https://github.com/users/aclater/projects/1), [scarletbook-rs#62](https://github.com/aclater/scarletbook-rs/issues/62) |
| 2026-11-01 | sacdfs 0.1.0 released without a release candidate, on scarletbook v0.5.0 | Owner: "dont wait for me on tags - I'm gonna be AFK and you are in the drivers seat". The scope in #45 was met: the figures were measured on the release code (#37), the oldest claimed distributions passed (#58) and the release workflow's dry run passed. No release candidate: the workflow refuses a tag that isn't exactly Cargo.toml's version, and its dry run already builds, tests and checks everything a tag publishes. Not on scarletbook 0.5.1: every published figure was measured on 0.5.0, and 0.5.1's changes (stored timecodes, cheaper provisional seeks, the cancel bound) are not on 0.1.0's paths. It moves with #28 in 0.2.0. Trade-off: the GHCR image is first published at the final tag, so the NAS test (#21 part 2) runs after the release. | [sacdfs#45](https://github.com/aclater/sacdfs/issues/45), [#70](https://github.com/aclater/sacdfs/pull/70) |
| 2026-10-31 | Prefer scarletbook-rs over our own code: tools offload SACD and DSD work to scarletbook when its result is bit-identical and within an agreed performance leeway (no more than 15 % slower on the measure that matters, and still within the tool's published targets) | Owner: "we don't want to maintain code across projects". One implementation means one place to fix, fuzz, harden and speed up. The leeway trades a little speed for much less duplicated code. Bit-identical output is never traded. Whenever an offload is slower than the code it replaced, the consumer files a performance issue on scarletbook-rs with the numbers, and scarletbook optimises back to the earlier performance (an exception to its throughput pause). | [sacdfs#28](https://github.com/aclater/sacdfs/issues/28), [pysacd#85](https://github.com/aclater/pysacd/issues/85) |
| 2026-10-31 | sacdfs deployment: server-side on the NAS is primary (clients see files over SMB/NFS); client-side over network shares is secondary | Latency: server-side seeks read the images locally and pay about one network round trip, while client-side pays one per probe. Any client OS works, and SMB users are served. It needs persistent file IDs for NFS and a container that serves its own SMB/NFS, because appliance NAS sharing services can't see a FUSE mount inside a container. | [sacdfs#17](https://github.com/aclater/sacdfs/issues/17) |
| 2026-10-31 | scarletbook-rs: pause throughput work once the open performance issues (#27, #31, #61, #62) are resolved; benchmarks become a regression check | 0.3.0 is 2.8–4.0x `sacd_extract` and faster on one core than every other decoder measured. Decoding is no longer the bottleneck: one stream needs about 1/78 of a core, and storage and network I/O dominate whole-library work by about 10x. Effort goes to latency, concurrency, 1.0 and sacdfs's PCM conversion. | [scarletbook-rs#62](https://github.com/aclater/scarletbook-rs/issues/62) |
| 2026-10-31 | sacdfs PCM: add a "wide" (~80 kHz) filter option at 176.4/352.8 kHz; default stays 40 kHz | Philips blind tests (Nuijten and Reefman, AES 5399, 2001) found 80–100 kHz filters undetectable and 50 kHz detectable. Reefman and Janssen and Stuart (JAES 52(3), 2004) favour 48–100 kHz. Weiss's 40 kHz stays the safe default for unknown playback chains. The option costs no speed. To be re-read from legitimate copies before release. | [sacdfs#11](https://github.com/aclater/sacdfs/issues/11) |
| 2026-10-31 | sacdfs: `--flatten` collapses single-image folder chains (off by default; top level kept); hybrid discs' CD layer and flag not shown | Libraries nest each image several folders deep, which is tedious to browse. Off by default so existing paths don't change. The CD layer isn't in SACD images at all, and no player uses the hybrid flag. | [sacdfs#13](https://github.com/aclater/sacdfs/issues/13), [#14](https://github.com/aclater/sacdfs/pull/14) |
| 2026-10-31 | One overview repository and a cross-repository board; repositories stay where they are | One front door for the projects. Moving them into an organisation would break the clean environment's access tokens, PyPI trusted publishing and the CI services. | this repository |
| 2026-10-31 | sacdfs: no DoP; FLAC deferred; DSF and WAV side by side; 176.4 kHz / 24-bit default; `--pcm-gain` offered (0 dB default) | DoP files play as noise on equipment that doesn't support it, and players already make DoP from DSF. Compressed FLAC's size is unknown until encoded, which breaks a fast filesystem. 176.4 kHz is DSD64 divided by exactly 16. The 0 dB default can't clip. | [sacdfs#11](https://github.com/aclater/sacdfs/issues/11) |
| 2026-10-31 | sacdfs PCM: band-limit to 30–40 kHz (default 40) following Daniel Weiss; ~105–110 dB stopband accepted | No published dB standard exists. Weiss (Saracon) is the most authoritative voice: a proper decimation filter keeps DSD's noise out. Independent measurements found converters of this class transparent. A deeper stopband costs speed for nothing shown to be audible. | [sacdfs#11](https://github.com/aclater/sacdfs/issues/11) |
| 2026-10-31 | sacdfs relicensed to GPL-3.0-or-later | Lets it draw on GPL and LGPL code, such as pysacd's DSD-to-PCM converter. GPL-3.0 also accepts Apache-2.0 and GPL-3.0 code, which GPL-2.0 does not. SACD parsing and DST still come only from scarletbook. | [sacdfs#12](https://github.com/aclater/sacdfs/pull/12) |
