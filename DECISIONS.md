| 2026-11-01 | pysacd-extract: when an area's **last** frame is the only missing one and the frames before it are silence, warn and exit 0 (still fill it with silence). This is a **workaround** for early Sony discs | Owner: "yes, but make sure we note that this is a work-around based on what we saw with early sony discs". Four discs of four titles (Master TOC 1.00, pressed 2000–2001) have a last area sector with no audio sector header. pysacd filled the final 1/75 s with silence, which is correct, but failed the run, so good discs landed in the failed pile in batch runs. A library check found the same 4 tracks' extracts identical to sacdfs's output. Alternative: keep failing on any missing frame (strict, but the same false failures). Trade-off: a truly damaged final frame that happens to follow silence would pass with only a warning. Revisit if other discs show the pattern. | [pysacd#93](https://github.com/aclater/pysacd/issues/93) |
| 2026-11-01 | scarletbook-rs DST decoder: both separate x86-64-v3 archives **and** run-time CPU feature dispatch (AVX2/FMA in one generic binary) | Owner: "i want that comment its the right path", then "its a both AND - that's ok". The x86-64-v3 build was about 14 % faster on DST (scarletbook-rs#146), but consumers ship generic builds: pip can't choose a wheel by CPU level, and sacdfs's container must run on every NAS. Dispatch inside the library gives every generic build the gain, with no packaging change or archive selection, as scarletbook-pcm already does since 0.5.3. The v3 archives come first (already planned) and help consumers that can choose an archive now. Dispatch follows, for every generic build. Trade-off: a small `unsafe`/`target_feature` surface in the core crate, and testing both paths for bit-identity. | [scarletbook-rs#146](https://github.com/aclater/scarletbook-rs/issues/146) |
| 2026-11-01 | sacdfs switches its WAV conversion to scarletbook-pcm 0.5.3 and deletes its own converter (about 1,450 lines); WAV output version 3 | This meets the owner's earlier condition ("keep ours, switch later": switch once scarletbook-rs #170–#173 are fixed and the numbers are within the leeway). Measured on 0.5.3, one thread, default filter: 298× against 315× (−5 %, generic build) and 273× against 316× (−14 %, x86-64-v3); the worst case is −14.8 %, within the 15 % leeway. The 30 kHz and wide filters are 9–39 % faster. Every target is met: stopband ≥ 109 dB, exact digital silence including area edges, determinism. DSF output is unchanged (93/93). Trade-off: WAV bytes change once (version bumped, golden hashes re-pinned), and the mount's WAV reads are 3–10 % slower. | [sacdfs#84](https://github.com/aclater/sacdfs/issues/84), [#85](https://github.com/aclater/sacdfs/pull/85) |
| 2026-11-01 | sacdfs: multichannel copies get ` (Multichannel)` added to their album tag by default, with an option to turn it off; names from the tag layer win | Owner accepted the recommendation ("i take your recommendation"). Tag bytes no longer have to match old extracts; only the audio must be bit-identical (sacdfs#28 row above), and `sacdfs verify` compares audio only. | 2026-11-01 | sacdfs adopts scarletbook's DSF writer (`output::Layout`) and deletes its own; the conformant ID3v2.4 `TCOP` (year prefixed) is accepted, and the DSF output version is bumped | Owner: "i dont care about roons play history or churn". 53 of 93 real-disc DSF files stay byte-identical. The other 40 differ only in `TCOP`: scarletbook writes the year before the copyright, as ID3v2.4 asks. The audio is unchanged. Keeping our writer would only protect byte identity with old extracts (Roon's history carry-over) and avoid one re-scan of those files. The owner doesn't need either, and one copy of the writer is the offload goal. Alternative: ask scarletbook for a TCOP-as-stored option, and keep our writer until then. Trade-off: the changed files show new times and identity once, and no longer match old extracts byte for byte (`sacdfs verify` compares audio only, so it's unaffected). | [sacdfs#28](https://github.com/aclater/sacdfs/issues/28) |
| 2026-11-01 | scarletbook-rs: the PCM fixes ship as 0.5.3, with the Rust API breaks from the 1.0 audit held for a later 0.6.0 (then 1.0). The clean side had proposed one 0.6.0 | Owner: "I wanted to get fixes to consumers now, then they can handle api breaks when 0.6.0 comes". 0.5.3 changes PCM output, not the API (semver-checks passes for a patch): exact digital silence, new Low/Wide stopband edges, a new first stage, and area edges as the idle pattern (scarletbook-rs#176). So **within 0.5.x, PCM bytes are not stable**. Consumers pin exact versions (sacdfs a git tag, pysacd a checksummed lock) and must keep doing so. Once on crates.io, use `=0.5.x` where PCM bytes matter. sacdfs bumps its WAV output version whenever scarletbook changes PCM bytes. Alternative: one 0.6.0, with PCM fixes and API breaks together. That's a single disruption, but the fixes would come later. Trade-off: two updates for consumers instead of one, and output-changing behaviour in a patch release. | [scarletbook-rs#176](https://github.com/aclater/scarletbook-rs/pull/176), [#39](https://github.com/aclater/scarletbook-rs/issues/39) |
| 2026-11-01 | sacdfs keeps its own DSD-to-PCM converter for now; it switches to scarletbook-pcm once scarletbook-rs #170-#173 are fixed and a new measurement is within the leeway | Owner chose "keep ours, switch later". The wide and 30 kHz filters miss sacdfs's stopband targets, and DSD silence isn't exact digital silence (up to -62 dBFS at area edges with the wide filter). Alternative: switch now. It is still 171x real time, and the duplicate code goes today. Trade-off: about 1,600 lines of converter stay ours a while longer. | [sacdfs#84](https://github.com/aclater/sacdfs/issues/84) |
| 2026-11-01 | Source check of the wide (~80 kHz) PCM filter decision: the Reefman and Janssen part is confirmed from a legitimate copy; Nuijten and Reefman (AES 2001) and Stuart (JAES 52(3), 2004) are still to be read | The owner now has an Academia.edu subscription and fetched the papers. | 2026-11-01 | sacdfs tag layer: edits in a separate tags directory, one file per disc keyed by TOC identity; edits made out-of-band (importer from extracts, beets-pysacd export, CLI/TOML), with no writable mount; art embedded only when a disc's tags name it | Owner chose the recommended option on all three questions. The images' dataset stays read-only, and edits survive renaming or moving an ISO. A writable mount would mean accepting multi-GB whole-file rewrites from taggers over FUSE/NFS/SMB, then verifying the audio unchanged: high risk for a convenience the importer and beets already provide. Embedding art only on request keeps the default output byte-identical, which is how Roon carries play history over. Trade-off: no tagging straight from a player's file-tag editor. | [sacdfs#81](https://github.com/aclater/sacdfs/issues/81) |
| 2026-11-01 | sacdfs is architected for storage reclamation: users can delete their DSF/DFF extracts and keep only the SACD images, losing nothing | Owner: "a value of using sacdfs is reclaiming storage space - so that's what i want to architect for" ... Deletion needs, in order of what blocks it: folder art and sidecar files served, per-file verification before deleting, byte-identical default output (so players carry history over; Roon did), performance at least that of local files, beets following the ISOs, a tag layer for edits, small caches only, and simple same-host deployment. | 2026-11-01 | DSD-to-PCM conversion: keep scarletbook-rs's clean implementation (scarletbook-pcm, #130) rather than adopting an existing code base; measure it against the consumers' converters after 0.5.2 (quality, ≥ 100× real time, within the 15 % leeway, determinism) | Owner asked whether PCM must be clean room or could adopt open-licensed code, and approved the plan ("good plan"). The clean converter already exists, was written from pre-2006 literature, and has no licence or patent questions. If it falls short, file the gap upstream with numbers; as a fallback, allow the clean side to consult permissively licensed standalone DSP code outside any SACD/DST repository, recording each source. Trade-off: possibly some speed or quality work upstream, in exchange for clean provenance. | [scarletbook-rs#130](https://github.com/aclater/scarletbook-rs/issues/130), [#40](https://github.com/aclater/scarletbook-rs/issues/40) |
